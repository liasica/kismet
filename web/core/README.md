# @kismet/core

纯计算包，不碰网络与 DOM，Web 端与命令行都直接引它。两个子模块：

| 入口 | 内容 |
| --- | --- |
| `@kismet/core` | 八字排盘，`src/bazi/` |
| `@kismet/core/region` | 中国行政区划查询，`src/region/` |

数据本体放在仓库根的 `data/`，是语言中立的 JSON，Go 服务端读同一份：`data/region/` 是区划，`data/fixtures/charts.json` 是约束两份实现一致的黄金基准。

## 八字排盘

入口是 `baziPaipan(input, options)`，返回可直接 `JSON.stringify` 的 `BaziChart`。

```ts
import { baziPaipan, baziToText } from "@kismet/core"

const chart = baziPaipan(
  {
    year: 1990, month: 5, day: 3, hour: 12, minute: 30,
    gender: "male", name: "某某", longitude: 114.0833,
  },
  { useTrueSolarTime: true, qiYunPrecision: "hour" },
)

console.log(baziToText(chart))
```

命令行入口用于跟现有排盘工具逐项对照：

```bash
pnpm paipan --date 1990-05-03 --time 12:30 --gender male --lng 114.0833 --true-solar --qiyun hour
pnpm paipan --date 1990-05-03 --time 12:30 --gender male --json
pnpm paipan --help
```

## 直接复用与自实现的分工

干支、节气、农历换算不自行推导，全部走 [`tyme4ts`](https://github.com/6tail/tyme4ts) 1.5.2，其节气算法取自寿星天文历，精度到分钟。

| 项目 | 来源 | 用到的接口 |
| --- | --- | --- |
| 四柱（年以立春为界、月以十二节为界） | tyme4ts | `SixtyCycleHour.fromSolarTime` 的 `getYear` / `getMonth` / `getDay` / `getSixtyCycle` |
| 地支藏干（本气、中气、余气） | tyme4ts | `EarthBranch.getHideHeavenStems` |
| 十神 | tyme4ts | `HeavenStem.getTenStar` |
| 纳音 | tyme4ts | `SixtyCycle.getSound` |
| 十二长生 | tyme4ts | `HeavenStem.getTerrain` |
| 旬与旬空 | tyme4ts | `SixtyCycle.getTen` / `getExtraEarthBranches` |
| 胎元、胎息、命宫、身宫 | tyme4ts | `EightChar.getFetalOrigin` / `getFetalBreath` / `getOwnSign` / `getBodySign` |
| 起运时间折算 | tyme4ts | `ChildLimit` 与四个 `ChildLimitProvider` |
| 节气交节时刻 | tyme4ts | `SolarTerm.fromIndex` / `fromName` |
| 干支纪年、干支纪月 | tyme4ts | `SixtyCycleYear` / `SixtyCycleMonth` |
| 五行生克关系 | tyme4ts | `Element.getReinforce` / `getRestrain` / `getReinforced` / `getRestrained` |
| 真太阳时（经度差与均时差） | 自实现 | `src/birth/equation-of-time.ts` |
| 夏令时区间 | 自实现 | `src/birth/daylight-saving.ts` |
| 早晚子时分支 | 自实现 | `pillars.ts` |
| 神煞查法表与匹配 | 自实现 | `src/bazi/data/shensha.ts`、`shensha.ts` |
| 五行强弱评分 | 自实现 | `elements.ts` |
| 大运、小运干支 | 自实现 | `fortune.ts` |
| 结果数据结构与竖排文本 | 自实现 | `types.ts`、`text.ts` |

大运与小运的干支自己推而不用 `DecadeFortune` / `Fortune`：那两个类从 `tyme4ts` 内部重算的八字取月柱与时柱，选择晚子时算当天时时柱会与本模块不同，自己推可以保证跟本模块的四柱一致。

所有查表数据与算法分离：`data/constants.ts` 放干支基础常量与月序，`src/bazi/data/shensha.ts` 放神煞查法，`data/daylight-saving.ts` 放夏令时区间。藏干、纳音、五虎遁、五鼠遁的表由 `tyme4ts` 提供，模块不再抄一份；`pillars.ts` 另外导出了 `monthStemOf`（五虎遁）与 `hourStemOf`（五鼠遁）两个公式函数，测试用它们跟 `tyme4ts` 的排法交叉核对。

## 排盘规则

### 时间校正

输入一律当作北京时间（UTC+8）的**钟表读数**，依次过三道校正，每道的偏移量都留在 `BaziChart.time` 里：

1. **夏令时**：落在中国 1986 至 1991 年夏令时区间的读数回拨一小时，得到标准北京时间。1992 年起中国不再实行夏令时，开关对其他年份无作用。
2. **经度差**：地方平时 = 标准北京时间 + (经度 − 120) × 4 分钟。
3. **均时差**：真太阳时 = 地方平时 + 均时差，取值范围约 −14 至 +17 分钟。

均时差用 Meeus《Astronomical Algorithms》第 2 版的自包含公式：主式取第 28 章式 28.1，太阳平黄经与中心差取第 25 章，黄赤交角取式 22.2，章动只取升交点主项。

这里刻意**不用**寿星天文历的级数。Go 服务端要排出与 Web 端逐位相同的盘，而 `tyme4go` 没有导出那组函数，两边只有共用同一套自包含公式才能保证一致；代价是精度约 2 秒，寿星级数能做到 0.6 秒，但对只取到分钟的排盘没有影响。

精度实测：对 Meeus 书中例 28.1（1992-10-13）算得 +13m42.0s，印刷值 +13m42.6s；与寿星级数逐日比对 1887、1893、1904、1950、1990、2024 六年，最大相差 2.02 秒；全部 54 个基准用例在两种算法下的取整结果完全相同。

真太阳时结果截到分钟：输入本身只到分，秒位是校正累积出来的，留着会让起运折算的时辰位漂移。

### 四柱

- **年柱**以立春交节时刻为界，立春前属前一年，不是正月初一
- **月柱**以十二节为界，立春起为寅月，月干合五虎遁 `月干 = (年干序 % 5 × 2 + 2 + 月序) % 10`
- **日柱**六十甲子连续计数，`(JDN + 49) % 60` 与 `tyme4ts` 的排法在连续 400 天上逐日一致，基准 1949-10-01 为甲子日
- **时柱**子时 23 至 1、丑时 1 至 3，依此类推，时干合五鼠遁 `时干 = (日干序 % 5 × 2 + 时支序) % 10`

23:00 至 23:59 这一小时按 `lateZiAsNextDay` 分两派，时干各自跟随所用的那个日干，年柱与月柱两派相同。

### 派生项

藏干标本气、中气、余气三层，天干与每一位藏干都标十神。每柱另有：日干在本柱地支的十二长生（问真称「星运」）、本柱天干在本柱地支的十二长生（问真称「自坐」）、纳音、本柱自身的旬空，以及本柱地支是否落在日柱旬空内。

神煞第一版实现十四项：天乙贵人、太极贵人、文昌、驿马、桃花（咸池）、华盖、羊刃、将星、金舆、红鸾、天喜、孤辰、寡宿、魁罡。每条写成「基准位 → 命中值」的查表规则加一个 `note` 记出处与流派分歧，匹配由 `matchShenSha` 一个函数完成，没有分支堆。

五行强弱按可替换的策略计分，默认策略 `weighted` 的权重是天干 1、本气藏干 1、中气 0.5、余气 0.3，月令那一柱的地支与藏干再乘 1.5。同类取与日主同五行的比劫加生日主的印星，按同类占比分旺、偏旺、中和、偏弱、弱五档。另有一个只数干支个数的 `count` 策略作对照。换策略用 `createWeightedStrategy` 造一个再注册进 `ELEMENT_STRATEGIES`，或者自己实现 `ElementStrategy` 接口。

### 大运、流年、流月

阳年男与阴年女顺排，阴年男与阳年女逆排。大运干支从月柱起步每步走一位、每步十年；小运从时柱起步按虚岁逐年走一位。

起运按顺排数到下一个节、逆排数到上一个节的时间差折算，3 天折 1 岁、1 天折 4 个月、1 时辰折 10 天。流月以十二节为界，交节时刻取自寿星天文历。

## 选项

命理各家在时间口径与折算方式上分歧较大，下面每一项都是流派选择而不是唯一正解，默认值取自本项目的规则文档。

| 选项 | 默认 | 含义与分歧 |
| --- | --- | --- |
| `useTrueSolarTime` | `false` | 真太阳时校正。为 `true` 时必须给 `longitude`，不给会抛错而不静默降级 |
| `useDaylightSaving` | `false` | 把输入按夏令时钟表读数处理。夏令时结束日 01:00 至 02:00 这一小时在钟表上出现两次，仅凭读数无法区分，本实现按夏令时处理 |
| `lateZiAsNextDay` | `false` | 晚子时归属。`false` 时日柱用当天并按当天日干推时干；`true` 时日柱用次日、时干跟随次日日干 |
| `qiYunPrecision` | `"hour"` | 起运折算精度。`hour` 折到时辰，对应 `tyme4ts` 的 `LunarSect2ChildLimitProvider`，与问真八字同一档；`day` 只折到日，丢掉余下的时辰，对应 `China95ChildLimitProvider` |
| `shenShaSkipBasePillar` | `false` | 基准柱自身是否还标该神煞。问真八字不标：将星以年支查，年支午自身即是将星，它只在时柱标将星。以日柱整体判定的魁罡不受此项影响 |
| `maxAge` | `100` | 流年输出到多少虚岁 |
| `elementStrategy` | `"weighted"` | 五行评分策略名 |

`tyme4ts` 另外提供 `DefaultChildLimitProvider`（折到分）与 `LunarSect1ChildLimitProvider`（把出生与交节都归到时辰边界再按整数折算）两档起运口径，本模块没有接到 `qiYunPrecision` 上，需要时在 `src/bazi/fortune.ts` 的 `QI_YUN_PROVIDERS` 里加一档。

## 与问真八字的核对

### 问真的时间口径

核对过程中查明了问真（https://pcbz.iwzwh.com）自己的口径，对齐它需要按下面设置：

- **四柱与起运都按真太阳时排**，北京时只用于显示。它排盘时向后端传的是真太阳时时刻
- 页面上那个「真太阳时」勾选**不参与排盘**，只在保存案例时被读取，排盘恒用真太阳时
- 真太阳时**含均时差**，不只是经度差
- 默认设置下 **23 点即换日**，相当于本模块 `lateZiAsNextDay: true`；本模块默认 `false` 是任务规则的取值
- 起运折算折到时辰，相当于本模块 `qiYunPrecision: "hour"`
- 神煞不在基准柱自身标注，相当于本模块 `shenShaSkipBasePillar: true`

### 已知差异

1. **神煞集合不同**。问真在基准盘那一造还给出福星贵人、国印贵人、德秀贵人、红艳煞、童子煞、拱禄、吊客、地网，本模块第一版只实现十四项常用神煞，不含这些。两边都有的太极贵人、羊刃、将星、寡宿逐柱一致。
2. **华盖的查法基准不同**。问真把华盖标在月柱辰，说明它以日支起（日支辰，申子辰见辰）；本模块按主流的年支起（年支午，寅午戌见戌），基准盘那一造无戌因而不出华盖。改基准只需把 `src/bazi/data/shensha.ts` 里华盖那条的 `base` 从 `yearBranch` 换成 `dayBranch`。
3. **晚子时的时干处理不同**。问真开了早晚子时后只把日柱退回当日，时干仍按次日日干起：1904-08-21 23:34 它给 丁亥 日配 壬子 时，壬来自次日日干戊。本模块按任务规则让时干跟随所用的那个日干，给 庚子。`tyme4ts` 的 `LunarSect2EightCharProvider` 与问真同一口径，本模块没有采用。
4. **均时差精度不同**。例 1 本模块算出 06:59:24、问真给 07:00，相差 36 秒而 07:00 正是卯辰交界，时柱因此从癸卯变甲辰，命宫与身宫跟着变。本模块的均时差与寿星天文历级数逐日相差不超过 2 秒，问真那 36 秒的差距远超两种算法之间的分歧，06:59:24 是更接近真值的一侧，因此没有为对齐问真而调整算法。
5. **五行给法不同**。问真只给月令的旺相休囚死，不给分值；本模块两者都给，分值口径是自定义的加权计分，无从与问真比对。

## 数据来源与适用范围

- 干支、节气、农历：`tyme4ts` 1.5.2，节气算法源自寿星天文历，适用年份随其 VSOP87 截断级数，覆盖公元前 4000 年至公元 8000 年
- 均时差：Meeus《Astronomical Algorithms》第 2 版式 28.1 加第 25 章的太阳位置，自包含，不依赖天文级数表
- 夏令时：国务院 1986 年夏令时通知与 IANA 时区数据库 `Asia/Shanghai` 的 `PRC` 规则段，只覆盖 1986 至 1991 年
- 神煞查法：《渊海子平》《三命通会》的通行口诀，每条的出处与分歧写在该条的 `note` 里
- 出生地经纬度：见 `src/region/index.ts` 的说明

## 与 Go 实现的一致性

仓库根的 `internal/bazi` 是本包的 Go 对应实现，供原生 app 等不能引 TypeScript 包的客户端使用。两边共用同一个 tyme 库（tyme4go 与 tyme4ts 同代），自实现的部分逐个移植，输出的 JSON 结构逐字段一致。

约束方式是黄金基准：

```bash
pnpm fixtures      # 本包生成仓库根 data/fixtures/charts.json，54 个用例连同完整 BaziChart
go test ./...      # 在仓库根运行，Go 侧读同一份文件跑同样输入，逐字段比对
```

基准覆盖真太阳时、夏令时、早晚子时两派、立春与十二节的交节边界、四组顺逆、两档起运精度、神煞的两种口径、两个五行策略。改动任何一侧的排盘逻辑后都要重跑这两条命令。

为此有两处刻意的设计：均时差用自包含公式（见上），以及 `elements` 的 `scores` 与 `seasonalState` 用英文键（`wood`/`fire`/`earth`/`metal`/`water`），中文只出现在值与界面上 —— Go 与移动端解析中文 JSON key 很别扭。中英映射在 `ELEMENT_KEYS` 与 `ELEMENT_NAMES`。

## 行政区划

`@kismet/core/region` 提供省、市、区县、乡镇四级查询，每级都带经纬度，真太阳时只用经度。

层级不固定，某一级缺位时直接跳过：直筒子市的镇街直接挂在市下，直辖市与省直辖县级行政区的区县直接挂在省下，港澳只有两级，台湾只有省、市、乡镇市区三级。调用方不要按固定级数写死流程，看返回条目自身的 `level`，再用 `hasTowns` 判断要不要往下取一级。

省市区三级随首屏加载，查询是同步的；乡镇 41350 条按省切成 31 个分片，用 `loadTowns` 异步取，不进首屏 chunk。Go 服务端不需要懒加载，启动时全量读入。

`searchRegions(query)` 跨级搜索，四级都能命中，返回完整地名与代码路径，界面拿 `path` 就能把联动面板定位到命中项。前三级用首屏数据即时搜；乡镇要先加载一份只含名称与代码的索引（`data/region/town-index.json`，约 210 KB gzip），单独一个 chunk、只在第一次搜索时加载。命中的乡镇不带经纬度，选中后用 `findRegion(code)` 取回完整条目，那时才加载所在省的分片。

匹配打分是完全相等 3 分、前缀 2 分、包含 1 分，同分时省市在前、乡镇在后，再按代码升序。Go 侧的 `Store.Search` 用同一套规则，同一个词在两端搜出来的顺序相同，由 `region_test.go` 的 `TestSearch` 约束。

数据来源与坐标精度的限制写在 `src/region/index.ts` 的文件注释里，生成脚本是 `src/region/scripts/build-data.mjs`。
